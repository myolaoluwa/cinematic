# Private client workspace

The workspace is a separate, owner-only area at `/workspace`. Each shoot has a private collection at `/collection/<token>`. Clients use the collection password in addition to the unguessable link; the photographer shares the password separately.

The UI is served from `dist/`. Vercel Node functions live in `api/`. Supabase supplies owner authentication, Postgres, and a private Storage bucket. No Supabase credentials belong in browser code.

## One-time setup

1. Create a Supabase project in a region appropriate for the photographer and clients.
2. In the Supabase SQL Editor, run [`20261120000000_private_client_workspace.sql`](../supabase/migrations/20261120000000_private_client_workspace.sql). This creates the tables and guarded RPCs, enables row-level security, and creates the private `client-galleries` bucket with a 50 MB image limit.
3. In Supabase Auth, create the photographer’s email/password account. Copy its user UUID; this is the only account permitted to manage collections.
4. Configure these Vercel environment variables for Preview and Production:

   | Variable | Value |
   | --- | --- |
   | `SUPABASE_URL` | Project URL, for example `https://your-ref.supabase.co` |
   | `SUPABASE_ANON_KEY` | Project’s public/anon key; used server-side for Auth and signed upload requests |
   | `SUPABASE_SERVICE_ROLE_KEY` | Project service-role key; secret, server-side only |
   | `OWNER_USER_ID` | Photographer’s Supabase Auth user UUID |
   | `WORKSPACE_SESSION_SECRET` | At least 32 random bytes, used to sign HttpOnly sessions and rate-limit identifiers |
   | `APP_ORIGIN` | Optional canonical site origin, such as `https://www.example.com`; omit to use the request host |
   Never add the service-role key to `dist/`, a `NEXT_PUBLIC_*` variable, or any client-side script. Keep the Supabase project’s anonymous access to the workspace tables disabled; the migration deliberately grants no table access to `anon` or `authenticated`.

5. Deploy a Vercel Preview from the project root (the directory containing `vercel.json`). Verify the photographer login, private upload, collection password, proof selection cap, selection submission/reopen flow, final-image download, expiry, republishing, and manual deletion before Production.

The repository includes a placeholder-only [`.env.example`](../.env.example). For local API testing, use Vercel’s local development environment with the same server-side variables; `python -m http.server` only previews the static pages and cannot run API functions.

## How it works

- Owner sessions are Supabase Auth sessions held in signed, HttpOnly, SameSite cookies. Every owner API request verifies the Supabase user and checks it against `OWNER_USER_ID`.
- Collection link tokens are random and only their SHA-256 hashes are stored. Passwords are generated by the server, stored as salted scrypt hashes, and shown only when the collection is created or its credentials are replaced.
- Proof uploads are resized in the photographer’s browser to a maximum 2,200 px JPEG preview before upload. Original final photos are uploaded as-is. Both are stored in the private bucket; supported formats are JPEG, PNG, WebP, and AVIF, up to 50 MB each.
- The client’s link and password are checked on the server. Client sessions are signed, scoped to one collection, and revalidated against its published state and expiry on every request.
- Selection changes and final submission run through database functions that lock the collection row. This enforces the selection cap and submit lock even if requests arrive concurrently.
- Password attempts are limited to 10 per 15 minutes per collection and hashed client IP. The raw IP is not stored.
- Viewing and downloading use signed URLs that expire within one hour (or at the collection expiry, if sooner). Refresh the gallery if a link expires. Proof previews are reduced in size, but—as with any browser-visible image—screenshots or copying cannot be fully prevented.
- Publishing proofs opens a 30-day client window. Publishing new client-facing photos or republishing resets the window. Expiry blocks client access but retains the files; deletion is a separate, permanent owner action.
- If collection deletion is interrupted, it remains marked for removal and can be retried from the workspace.

## MVP boundaries

- Shoot and collection creation is manual; enquiries do not create client records or collections.
- A shoot uses one shared client link and password. Clients do not need accounts.
- Credential delivery is manual. Share the link and password through separate channels.
- The workspace does not send email notifications, process payments, or support multiple staff accounts.

## Verification

From the project root:

```powershell
npm.cmd run build
npm.cmd test
```

The build checks public and workspace assets, Vercel routes, and JavaScript syntax for every API function. Unit tests cover credential hashing, signed sessions, origin checks, and input validation. Supabase-backed flows require the configured Preview environment for end-to-end verification.
